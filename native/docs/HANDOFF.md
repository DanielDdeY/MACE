# Entrega para los otros desarrolladores

El paquete verificado se genera bajo `native/dist/mace-native-1.4.2-win-x64-.../`. Usar `bin/mace_native.dll` de ese paquete y cotejar su SHA-256 con `build-info.json` o `SHA256SUMS.txt`. Para comprobar hardware en otro equipo sin herramientas de compilación, ejecutar `bin/test_mace.exe` desde la misma carpeta que la DLL siguiendo [la guía del grupo](TEAM_DIAGNOSTIC_GUIDE.md). El `.lib` sirve para consumidores C; Java FFM carga directamente la DLL. Las cabeceras publicadas definen el contrato C.

El Java actual enlaza los siete símbolos anteriores y no necesita cambios inmediatos. Para pruebas se puede fijar `MACE_NATIVE_LIB` o `-Dmace.native.lib` a la ruta absoluta del binario de `dist/`; así se evita cargar una DLL antigua de `app/lib/`. El script `packaging/package-windows.bat` del repositorio aún no consulta el ABI ni los hashes; Dev 3 deberá integrarlo cuando se trabaje en `packaging/`. Las nuevas funciones Java de caja negra deben usar el token V2: el puntero del hook heredado deja de ser válido al cerrarlo o apagar telemetría, y la DLL no puede saber si Java todavía lo lee.

`CP_GetAbiInfo` usa el descriptor FFM `FunctionDescriptor.of(JAVA_INT, ADDRESS, JAVA_INT, ADDRESS)`. La llamada `NULL, 0, &required` devuelve `-2` y `required=64`; después se reserva un segmento de 64 bytes alineado a 8. El ejemplo en `examples/ffm/NativeContractProbe.java` valida ABI 1.4 y tamaños 1584/28/16. Para los símbolos V2, consultar `ABI.md`; el LUID de cada GPU se obtiene con `CP_EnumerateGpuAdapters` y solo vale en la sesión actual de Windows. Dev 3 deberá usar `CP_EnumerateUserlandProcessesV2` y conservar PID + tiempo de creación hasta llamar a `CP_TerminateProcessV2`; pasar solo PID por la función antigua no detecta reutilización desde la lista previa.

Los registros heredados mantienen exactamente su layout. El campo `gpu_fan_rpm` ahora contiene RPM reales o cero; para distinguir métrica no soportada, usar V2. `build-info.json` indica `amdAdlxCompiled`: una DLL compilada sin el SDK ADLX mantiene inventario Radeon, pero no sus sensores. No copiar los encabezados ADLX al repositorio; el SDK oficial se pasa como ruta externa de compilación. La DLL no exige que el usuario final instale el SDK; requiere un controlador AMD compatible con ADLX.

`build-info.json` también indica `amdRyzenSdkCompiled`. Para que esa DLL lea temperatura de CPU AMD en otro equipo, el Ryzen Master Monitoring SDK debe estar instalado allí, con su controlador, y MACE debe ejecutarse elevado. Si falta, V2 conserva `NO_PROVIDER` y el uso de CPU de Windows sigue disponible. La potencia AMD continúa sin proveedor hasta acordar y validar su ámbito; véase [CPU AMD](AMD_CPU_TEMPERATURE.md).

La prueba física Radeon está documentada en `PHASE2.md`. Intel GPU, NVIDIA GPU, APU híbrida e Intel CPU requieren equipos adicionales. La temperatura CPU AMD depende del Ryzen Master Monitoring SDK instalado y de permisos; la potencia AMD sigue sin proveedor validado. La fase 4 añadió muestras por proceso, respuesta detallada de ventanas y un anillo temporal de caja negra; Dev 2/3/4 deben integrar la estrategia de fugas, persistencia y HUD, respectivamente. La fase 5 sincroniza los ciclos de vida. El proveedor ADLX conserva una sesión durante todo el proceso para evitar fugas de handles observadas al reinicializar ese controlador; no descargar la DLL MACE manualmente durante la ejecución. Véanse `EXTENSIONS.md` y `PHASE5.md`.
